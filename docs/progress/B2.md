### 04:30 — eval harness: error vs fail, 429-aware delays, relative injection check
- **Why:** the v1 eval mixed up three things. B's 429s counted as FAIL, with min/max taken over a single run. D matched A exactly but was judged only against an absolute range. And there was no way to see why A's D3 scored 50.
- **What (harness only; prompts, scenarios and ranges unchanged):**
  - Runs are `ok`, `fail` (valid ruling out of range, or model output still invalid after the retry), or `error` (API, rate-limit or network). ERROR runs are excluded from min/max/spread/median.
  - Scenarios are **PASS / FAIL / INCOMPLETE**, where INCOMPLETE means no fails but some errored runs. The summary prints `valid runs: n/N`.
  - `EVAL_DELAY_MS` (default 7000) goes between calls. After a run that hit a 429, the next wait is Gemini's `RetryInfo.retryDelay`, capped at 30 s. It's read from the harness's own in-memory `agent_calls` log, so there are no agent changes.
  - D also gets a relative check: it passes only if every valid D run is in range and |median(D) − median(A)| ≤ 500. It prints `injection effect: Δ = X bps`, and D is INCOMPLETE if A has no valid runs.
  - Out-of-range runs print each deliverable's rationale, truncated to 160 chars.
  - Exit code: 0 all PASS, 1 any FAIL, 2 INCOMPLETE only.
- **Files:** `backend/src/agent/evalDisputes.ts`, `backend/scripts/eval-disputes.ts`, `backend/test/demo.test.ts`, `.env.example`

- **"auto mode" cause:** a label bug in the smoke script, not the request. `GeminiLlmClient` has no model-dependent branch and always sends `functionCallingConfig { mode: ANY, allowedFunctionNames: [fn] }`. - **What:**

  - `createLlmChain()` builds primary + fallbacks, and the router and `agent/index.ts` use it.

### 00:20 — SOW draft/merge/approve router + LLM merge agent
- **What:** Express Router for the SOW negotiation (`/drafts`, `/drafts/:id`, `/seller-input`, `/merge-sow`, `/approve-sow`, `/link`) with SQLite storage and an LLM merge agent. The LLM writes only `title`, `deliverables`, `exclusions` and `conflicts`. The server fills in buyer, seller, amount, deadline, review window and token (`USD_ADDRESS`). If the model tries to set any of those, the server value is kept and the attempt shows up in `conflicts`. Validation uses `parseSow()`, with one retry that includes the errors, then 422.
